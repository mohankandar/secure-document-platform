## 2. Export as its own job (only when the setting is on)

- Setting `securedoc.processing.export-mode`: `inline` (today's behaviour, **default**) or `job`. With `inline` nothing changes; every existing test must pass unchanged.
- With `job`: where today the case is exported at the end of processing (`TriggerPackageProcessingService` → `ExportPackageDocumentsUseCase`), instead queue **one EXPORT job per enabled destination** for the case. Split documents get SPLIT_EXPORT jobs where today they are sent automatically.
- The case shows as **Ready for export** while it has export jobs not DONE. Derive it from the jobs; add a package status only if there is no clean way to derive it, and say why.
- **Workers:** a small fixed pool for export jobs (setting, default 4 per destination, 8 total). Worker scaling is P3, not now.
- **Pick-up:** in order (priority, then oldest), with `FOR UPDATE SKIP LOCKED`; a claim with a renewing lease and a **claim token**; the result is saved only if the token is still current. A job whose claim ran out goes back to READY and counts as an attempt.
- **Same request each time:** use the same idempotency key on every attempt for the same case run and destination, as `SDV_DELIVERY_V1.md` already defines (`Idempotency-Key: <sourceSubmissionId>`). Check the derived (split) destinations do the same.

## 3. Retries by code (design section 5)

| Result | What happens |
|---|---|
| LV-DLV-001, LV-DLV-002 (unreachable, timeout, 429, 500, 502, 503) | WAITING_RETRY, next try in **5 minutes**, up to **3** tries. **3 failures in a row across a destination's jobs → the destination is PAUSED**: its jobs stay READY/WAITING_RETRY without using attempts. A probe (the existing connection test) runs every **5 minutes**; on success the destination is WORKING again and its jobs go out **in order**. After the 3rd try of a job (destination not paused), NEEDS_IT. |
| Duplicate / already received | **DONE (exported)**, never retried, audited with `LV-DLV-009`. For Vero: an idempotent replay with the same key already answers success. Find out what a **409** from Vero means in `SDV_DELIVERY_V1.md` and Vero's own docs if available; if it means "same key, already received", map it to LV-DLV-009; if it means "same key, different content", keep it as LV-DLV-004. Report what you found. For split destinations, use their own contract the same way. |
| LV-DLV-003, LV-DLV-004 (refused the level or the file) | No retry. WAITING_FOR_YOU. |
| LV-DLV-005 (sign-in to the destination refused, credential missing) | The destination goes to NEEDS_IT (all its jobs wait), and this job is NEEDS_IT. |
| LV-DLV-007, LV-DLV-008 (answer not understood, not all confirmed) | Up to 3 tries, 5 minutes apart, then NEEDS_IT. |
| Anything else | NEEDS_IT with the code it has (LV-SYS-001 if none). |

- **The in-adapter immediate retries** (`withRetry` with 1–3 s sleeps in the SDV and derived adapters) do not run in `job` mode: one attempt per job run; the job does the spacing. In `inline` mode they stay as today.
- Timings (5 minutes, 3 tries, 3 in a row, probe every 5 minutes) are settings with these defaults.
- Every status change and every pause/resume is audited with its code. Codes and ids only.

## 4. Resend and the IT queue (API only; the screens are 0028)

- `GET` jobs WAITING_FOR_YOU for the tenant (case id, destination name, code, since), and `POST` resend for **many** jobs at once. Allowed for Processor and Supervisor (same capability as today's manual send). **A resend is one attempt:** success → DONE; failure → NEEDS_IT with `LV-DLV-015` and the failure's own code as the detail.
- `GET` jobs NEEDS_IT and destination states, and `POST` retry for IT Admin (existing technical retry capability). An IT retry puts the job back to READY (attempts reset) and, for a destination in NEEDS_IT or PAUSED, also lets IT set it back to WORKING.
- **Notification:** none yet (the shared notifications module comes later). Record an audit action that the notifications module can pick up later, and make NEEDS_IT jobs count in the support "needs attention" numbers.
