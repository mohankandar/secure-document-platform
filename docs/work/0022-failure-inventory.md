# Task 0022, Part B: failure inventory

Date: 2026-11-20. Branch: `feature/0022-followups-and-failure-inventory` (code as merged from `feature/sensitivity-levels`, plus Part A).

**What this is.** Every place found where LexaVault fails, refuses or stops something, one row each: 388 rows across all modules and the frontend. It is the input for the `LV-<AREA>-<NNN>` code list. **No final codes are assigned here**; the "Proposed area" column only suggests one. No code was changed for Part B.

**How it was made.** Four read-only surveys of the source (intake and scanner; processing, AI and redaction; review and delivery; sign-in, configuration, start-up and frontend). Each row points at code that was read. The surveys were merged, the 15 delivery rows the processing survey repeated were dropped in favour of the more detailed delivery rows, and the rest was renumbered. The highest-impact claims were checked again by hand (see "Other findings"). The four surveys used the same columns; where two rows describe the same condition from two sides (for example the API refusal and the screen that shows it), both are kept and the Notes say so.

**Privacy.** No redacted value, file name, person's name or secret is in this file. Where a message carries such a value, the row describes it ("followed by the source's document id") instead of quoting it.

## Behaviour shared by many rows (read once)

**How the main API turns an exception into a response** (`API/exception/GlobalExceptionHandler.java`; body `{errorCode, message, correlationId, timestamp}`):

| Exception | HTTP | errorCode | Message sent | Logged | Audited |
|---|---|---|---|---|---|
| `ValidationException` / `IntakeValidationException` | 400 | `VALIDATION_ERROR` / `INTAKE_<reason>` | the exception's own text | yes, reason code only | no |
| `IntakeExpiredException` | 410 | `INTAKE_EXPIRED` | own text | no | no |
| `IntakeConflictException` | 409 | its own code | own text | no | no |
| `NotFoundException` | 404 | `NOT_FOUND` | "&lt;Type&gt; not found: &lt;id&gt;" | no | no |
| `IllegalStateException` | 409 | `INVALID_STATE` | **the raw exception message, whatever it is** | no | no |
| `IllegalArgumentException`, type mismatch | 400 | `INVALID_ARGUMENT` | "Invalid request parameter" (the real text is dropped) | no | no |
| `MaxUploadSizeExceededException` | 400 | `FILE_TOO_LARGE` | "Upload exceeds maximum allowed size" | no | no |
| bean validation | 400 | `VALIDATION_ERROR` | field messages | no | no |
| unreadable JSON | 400 | `INVALID_REQUEST_BODY` | fixed text | yes | no |
| `AccessDeniedException` | 403 | `ACCESS_DENIED` | "Insufficient permissions for this operation" (or the thrower's text) | yes | `AUTHORIZATION_FAILED` |
| `CapabilityNotEnabledException` | 403 | `CAPABILITY_DISABLED` | own text | no | no |
| `SecurityContextException` (all sign-in admission refusals) | 403 | `SECURITY_CONTEXT_INVALID` | fixed: "Authenticated identity is not authorized for this tenant/application" | no | no (the audit action exists but nothing writes it) |
| `LicenseEnforcementException` | 403 (503 for a configuration error) | `LICENSE_*` | fixed text per reason | yes | `LICENSE_ENFORCEMENT_DENIED` (see the rollback note) |
| `TechnicalDependencyException` | 503 if retryable, else 502 | the `TechnicalFailureCode` | the adapter's fixed, safe text | yes | no |
| anything else (for example Spring's missing-header or optimistic-lock exceptions) | 500 | `INTERNAL_ERROR` | "An unexpected error occurred" | class name only | no |

- **Audit rows can be rolled back.** The audit adapter joins the caller's transaction and nothing in the backend uses `REQUIRES_NEW`. On `@Transactional` endpoints an audit written just before the exception is very likely rolled back with it (licence denials, in-request intake expiry). Not yet proven by a test.
- **The Scan Bridge** has its own handler (`SB/api/ScanBridgeExceptionHandler.java`, body `{errorCode, message}`): its own exceptions keep their status, `IllegalStateException` gives 503 `BRIDGE_LOCAL_STATE_FAILURE`, anything else 500 `BRIDGE_INTERNAL_ERROR`.
- **The frontend** (`UI/studio/data.ts errorMessage`) shows the server's `message` word for word whenever there is one; the static fallbacks appear only when there is no body.

**Processing stops ("Std incident" in the rows).** `APP/processing/service/TriggerPackageProcessingService` catches the failure, `ProcessingIncidentService.recordFailure` writes an incident (Support list), the document is marked FAILED with audit `DOCUMENT_PROCESSING_FAILED` ("dependency=…, code=…, retryable=…, attempts=…"), the case is failed with a second `DOCUMENT_PROCESSING_FAILED` and the technical hold starts. `APP/technical/service/TechnicalFailureTaxonomy` gives each code a stage, a category and the case-panel explanation. Any exception that is not a `TechnicalDependencyException` becomes `UNKNOWN_TECHNICAL_FAILURE` (not retryable).

**Screens for processing stops.** Support list and Problem page: title and sentence from `UI/studio/words.ts PROBLEM_REASONS[code]`, plus " It stopped at &lt;stage&gt;."; an unknown code shows "Processing problem" / "Processing stopped for a technical reason. The code is under Technical details." Case panel (with the technical-view capability): the taxonomy explanation plus "The original is kept until &lt;date&gt;, so the case can still be finished." Cases list: "Processing stopped". Without retry or review capability: "Technical support has been notified."

**Retries.** In-process: `APP/resilience/SelectiveRetryExecutor` (default 2 attempts, 250 ms linear backoff, cap 5 s; only retryable `TechnicalDependencyException`). Adapters (SDV, AI, polling) also retry inside themselves, so the attempts multiply. Support's "Retry processing" ignores the retryable flag; the older case-panel retry needs it. No scheduled job retries a delivery left in `RETRY_PENDING`.

**The two codes already in use.**
- `LV-INT-005`: an unknown sensitivity level at intake, taken as Standard (rows #17, #19). Returned as a warning on push and scanner create responses, audited as `INTAKE_SENSITIVITY_LEVEL_UNKNOWN`.
- `LV-DLV-003`: SDV refused the case's or a document's sensitivity level (rows #211, #216). Shown in Support and the case panel; not retried.

## Messages and records that can show content or a secret today (bug list for the design chat)

Nothing here was fixed (Part B changes no code). "Content" means document text, a redacted value, a file name or a person's name.

**Can show content or a name**
1. **Polling run history keeps raw exception text** (#34). `failureDetail` and the `POLLING_RUN_FAILED` audit detail hold up to 500 characters of whatever exception was thrown, unfiltered, shown to IT Admin. That includes the messages below that echo a source id, an identifier key or a file name, and any third-party text.
2. **Duplicate manifest id is echoed** (#49): "Duplicate external source document id in manifest: " followed by the source's id. Source ids can carry a case reference or a name.
3. **Domain file-name message contains the file name** (#55). The API hides it (generic 400), but any path that keeps raw messages exposes it (polling, #34).
4. **Watched-folder observations show the drop folder's name** (#61, #58, #59, #60, #39) in `GET /api/v1/intake/watched-folder/observations`. Drop folders are often named after the person or the case.
5. **Scheduled watched-folder scan errors are logged with their IO cause** (#57, #56), which names absolute paths including the drop folder.
6. **`DOCUMENT_EXPORTED` audit detail holds the original file name** (#178, #180 and #195 to #201). Task 0021 left it there; A2 of this task added the two level codes next to it and did not remove it (not asked).
7. **Local-folder delivery stores the full path with the file name** (#201, #200) as the delivery location and in the export record.
8. **File-share split delivery returns file names** (#222): `destinationReference` and `fileName` in the derived-delivery and attention responses, shown under Technical details and used as a fallback label in the case panel.
9. **Any `IllegalStateException` text goes to the screen word for word** (#291, #383, and the 409 rows such as #167, #169, #170, #172). Today's LexaVault texts are safe (enum names and ids), but a library, JDBC or Spring message, or one wrapping a cause, would go out unfiltered.
10. **The Scan Bridge keeps business identifiers on disk** while an item waits (#83); its GET session response includes them and the prepared file name.
11. **The no-access screen shows the signed-in email or user name** (#284). Intended, but it ends up in support screenshots.

**Can show a host, an address or uncontrolled remote text**
12. **OIDC discovery test stores and shows up to 300 characters of a raw HTTP or JSON error** (#241), which can name internal hosts or quote the remote answer.
13. **The identity provider's token-endpoint error body (up to 500 characters) is logged to the browser console** in every build (#277).
14. **Business-admin validation appends an inner exception message** (#286), for example a pattern compiler's text.
15. **A misconfigured AI pool node URL is echoed in the start-up error** (#328). A URL with embedded credentials would be printed in the log.

**Content left on disk after a failure** (not a message, recorded nowhere)

## Other findings the design chat should know

These are not leaks or silent failures, but they will shape the code list. Items marked "checked" were confirmed again by hand after the survey.

1. **There is no four-eyes rule** (#145). A supervisor can decide every finding and then approve final delivery themself. (The older review-task path has the opposite rule: only the assigned reviewer may approve.)
2. **"Already decided by someone else" never shows as intended** (#160, checked). `UI/studio/Review.tsx` looks for `err.code === 'CONFLICT'`, but the API client throws `{errorCode, …}` and no backend response uses `CONFLICT`. The person sees a failure line instead of moving on.
3. **Client mistakes come back as 500** (#7, #32, checked): a missing `Idempotency-Key` or `X-Content-SHA256` header, a missing file part, a wrong content type, or a null in the identifier map. The intake documentation promises 400. The Scan Bridge treats any 5xx as worth retrying and has no attempt limit (#82), so it retries these forever.
4. **The push size limit cannot be reached** (#5, #22, checked). The push source default is 250 MB, but the multipart limit is 50 MB, so 50 to 250 MB is refused as `FILE_TOO_LARGE`. An empty file is told "PDF size exceeds the configured source limit".
5. **Manual upload has no server-side PDF check** (#45). Only the MIME type is checked; a non-PDF labelled as PDF is taken in and fails later in processing. Machine intake does check (#62).
6. **Many different stops share one text.** Corrupt or password-protected PDFs (#113), all redaction-verification failures (#142), recovery exhausted (`PROCESSING_RECOVERY_EXHAUSTED`, not in the screen word list) and lock contention all show "Processing problem". On sign-in, about ten different causes (including IT faults) show the same no-access text, "your account has no LexaVault role" (#284).
7. **A missing AI model or a wrong API key reads as a bad answer** (#123, #128): `AI_REJECTED`, "the AI model's answer couldn't be used". In pool mode a missing model reads as "AI model wasn't available" instead (#117). Once page retries run out, a passing AI timeout or outage is marked not retryable (#127, #120), so the older Retry button disappears.
8. **Delivery 409 and refused levels look like bad set-up.** A 409 from SDV or a split destination becomes non-retryable `DELIVERY_DESTINATION_INVALID` (#204, #224). A split HTTP destination that refuses a level cannot produce `LV-DLV-003` (owner's answer to 0021: decided in the Shared Capabilities thread).
9. **A case can show FAILED although it was delivered** (#201 a left-over local folder, #195 a missing acknowledgement, #180 a run-number clash after delivery). Export preconditions (#178) show as an unknown technical failure, not a business reason.
10. **State conflicts use mixed status codes**: some are 400 `VALIDATION_ERROR`, others 409 `INVALID_STATE` with the raw domain text.
11. **Configuration states are recorded as refused people.** A disabled SDV, polling or push connection and a watched folder set up for another tenant return 403 and are audited as `AUTHORIZATION_FAILED`.
12. **Scanner intake may be refused for machine clients under OIDC** (#254): the scanner route is not treated as a machine route, so the human role check runs first. Unconfirmed; there is no OIDC test for that route.
13. **Codes that do not line up.** The screens know `MODEL_TIMEOUT` and `SDV_UNAVAILABLE`, which the backend never sends. The backend sends `PROCESSING_RECOVERY_EXHAUSTED`, `DELIVERY_RUNTIME_ERROR`, `DERIVED_DESTINATION_DISABLED`, `DERIVED_DELIVERY_RUNTIME` and `DERIVED_CONNECTION_TEST_FAILED`, which are neither in `TechnicalFailureCode` nor in the screen word list. Polling answers its 409 with the key `code`, not `errorCode` (#9). Every `TechnicalFailureCode` value is raised somewhere; `UNKNOWN_TECHNICAL_FAILURE` is only a fallback.
14. **Dead code.** `securedoc-worker`'s polling loop is never scheduled; `securedoc-agent`, `-redaction`, `-output` and `-storage` hold no runtime code; `RoleAuthorizationInterceptor` is not registered. Their rows (#387, #388) are kept for completeness.
15. **No health checks** for Ollama, Tesseract, storage or SDV in the actuator; the admin health probes swallow errors (#336 to #338).
