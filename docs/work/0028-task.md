## 1. Resend by the Processor
- New capability **EXPORT_RESEND** for Processor and Supervisor (and any role holding PACKAGE_APPROVE_DELIVERY today). The Waiting-for-you list and resend endpoints use it. Approving delivery stays Supervisor only.
- Add **"Resend all for one destination"**: `POST /api/v1/export-jobs/resend-all {destinationId}` puts every WAITING_FOR_YOU job of that destination back to READY (one attempt each, as a resend), in their original order. The single-case resend stays. The list endpoint returns the jobs grouped by destination with counts per code.

## 2. Pausing by evidence (replace "3 failures in a row")
- **Can't connect, timeout, 500/502/503:** run the destination's **health check at once** (the existing connection test; for the local folder: write and delete a test file).
  - Check fails → the destination is **PAUSED**; checked every 5 min (existing probe); resumes on its own, in order.
  - Check passes → **the case's own retry schedule** (section 3); the destination stays WORKING.
- **429:** not a failure. Wait for Retry-After (default 60 s if absent), and lower that destination's workers by one, back up by one after 10 minutes without a 429, never below 1. No attempt used, no pause.
- **All destinations fail their checks within the same 2 minutes** (and there are at least 2): raise one alert **"LexaVault can't reach its destinations"** (audit action and a Support incident, code LV-DLV-001 with detail `ALL_DESTINATIONS_UNREACHABLE`), do not pause any destination or count attempts; check again every 5 minutes; clear the alert when any check passes.
- **Backup rule ("answering but failing"):** if failures from **at least 3 different cases** reach one destination within **10 minutes** while its check passes, pause it as above. Settings for both numbers.
- Remove `pause-after-failures` / `pause-min-distinct-cases` logic from 0027 (keep the settings readable but unused, or remove them; say which).

## 3. A single failing case: a long retry schedule, one rebuild, then IT
- For LV-DLV-001/002 with a passing check, and LV-DLV-007/008: retry after **5 min, 15 min, 1 h, 4 h, 12 h** (setting: a list of delays). Before the **3rd** retry, **rebuild the export once** from the stored redacted copies (a fresh submission for the same case run, same idempotency rules as `SDV_DELIVERY_V1.md`: the destination must still recognise a repeat). Then NEEDS_IT.
- **Grouped IT alerts:** NEEDS_IT jobs for the same destination and the same code form **one group** (one incident, one notification audit action) with a count, "first failed at" and the case ids; `POST /api/v1/support/export-jobs/retry-group {destinationId, code}` retries all of them. Single-job retry stays.

## 4. Retention per destination
- A retention period per export destination: the master destination and each split (routing) destination, **set by the Business Admin** next to today's retention settings (API now, screen in 0029). Default: the current case retention for the master; for a split destination, the same unless set.
- Each copy's clock starts when **that destination confirms receipt**. **Nothing is deleted while any export job of the case for that copy is open.** The original follows the case's own retention rule, as today, but is never deleted while any export job of the case is open (needed for the rebuild).
- The case counts as fully exported only when all its exports are done. Reports and audit counts unchanged.

## 5. Export state for the screens
- `GET /packages/{id}/export-jobs` and the Cases list response carry the export state for 0029's "Exporting" status: READY, DESTINATION_PAUSED, WAITING_FOR_YOU, NEEDS_IT (and EXPORTED / NONE). Add it to the list response if it can be done without a heavy query; say how.

## Tests
- Each rule above with a fake destination: check fails → pause → resume in order; check passes → the case's schedule with the rebuild before the 3rd retry, then NEEDS_IT; 429 → wait and fewer workers, no attempt; all destinations down → one alert, no pause, no attempts; 3 different cases in 10 minutes with a passing check → pause; grouped IT alert and retry-group; resend-all keeps order; Processor can resend, cannot approve delivery.
- Retention: a split copy is not deleted while its job is open or before its own period after receipt; the master and split clocks are independent; the original is kept while any export job is open.
- `inline` mode: the full existing suite unchanged.
