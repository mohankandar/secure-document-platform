Written 2026-11-26 by the LexaVault design chat. Queue C, next. Standing rules (`QUEUE.md` rules 8–11). Report `docs/work/0102-report.md`. Migrations 08x if needed. Browser tests on `LV_E2E_PORT_BASE=15375`.

**Source:** owner's test 2026-11-25, finding U3, with the owner's rule (`Test-Run-2026-11-25-Findings.md`).

**What happens:** the password-protected drop (contract 779001126006, one PDF, manifest listing it) was refused and moved to `_problem` correctly, but it left a case behind: 0 documents, "New, Waiting for documents", in "In progress" on the dashboard, which nobody can close or remove.

**Owner's rule:** a case is created only when **every** file the manifest lists has been taken in. If any file can't be taken (missing, password-protected, wrong type, too big, or anything else), **no case is created**; the drop is recorded as an intake problem with its reason (the existing LV-INT codes), the folder goes to `_problem` (the archive for refused drops), and the problem shows in the **Reports** intake view, never on the cases dashboard.

1. Red first: a drop with one good and one password-protected file, and one with a listed file missing, each leave no case and one intake-problem record with the reason.
2. Fix (check every file before the case is made, or remove the half-made case in the same transaction; crash-safe with the multi-node claim rules of `MULTI_NODE_WATCHED_FOLDER_COORDINATION.md`).
3. Existing stuck cases like 779001126006: an upgrade step closes them as "refused at intake", out of the dashboard, kept in reports.
4. Same rule for file polling if it has the same gap; say in the report.
