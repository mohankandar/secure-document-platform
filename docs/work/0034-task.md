## What to build
1. **A clean-up run** inside the existing lifecycle maintenance (the purge scheduler, `securedoc.lifecycle.purge-*`), not a new scheduler:
   - removes `pipeline_jobs` rows in **DONE** or **STOPPED** whose last change is older than the setting **`securedoc.processing.export-jobs.keep-finished-days`** (default **90**, allowed 7 to 3650; a bad value stops start-up with a clear message, code LV-SYS-005);
   - **never** removes a job in any other status (READY, RUNNING, WAITING_RETRY, PAUSED, WAITING_FOR_YOU, NEEDS_IT);
   - never removes a job of a case whose copies are still inside their retention period (task 0028), so retention can still find its jobs;
   - removes in batches (setting, default 1,000 rows per batch), so a large backlog never locks the table for long;
   - also removes **CLEARED** reachability alerts (`export_reachability_alerts`) older than the same period.
2. **Audit:** one record per run that removed anything: `PIPELINE_JOBS_CLEANED` with the count and the cut-off date only (codes and numbers, no case ids).
3. **Nothing else changes:** Reports, the compliance report and the audit trail must give the same answers before and after a clean-up (check which of them read `pipeline_jobs`; if one does, say how it still works for a period older than the cut-off, or keep those jobs and say so).
4. Works in `inline` mode too (where the table is empty, the run does nothing).

## Tests
- Old DONE and STOPPED jobs removed; recent ones kept; open jobs of any age kept; a job of a case still inside its retention kept; batches; the audit record; the setting's bounds and the start-up stop.
- The PostgreSQL test class (throwaway database) for the delete query and its index use.
- Full backend build and tests, `npm run test:standalone`, the no-redacted-value check and the compliance report check (throwaway containers only).
