## Build
1. **Stages as jobs.** `TEXT`, `FIND`, `REDACT` jobs per **document** in `pipeline_jobs`, next to `EXPORT`. Workers per stage pick jobs as export workers do (claim lock, `SKIP LOCKED`, queue number order). Each step calls the existing service for that step; no step's logic changes.
2. **Gates.** A case moves on only when every one of its documents is through a stage: all `FIND` done → Review if any finding needs a person (as today), else `REDACT`; all `REDACT` done → the case is Ready for export and its `EXPORT` jobs are queued (P1, unchanged). Review stays a person, not a queue.
3. **Claim with a fencing number (fixes #342).** Each claim carries a claim number; a worker's save only counts if its claim number is still current. A worker that lost its claim (paused, cut off) can't overwrite the newer worker's result. Claims are renewed while working.
4. **A server stops mid-job:** the claim expires, the job goes back to the queue and the attempt counts. After **3** attempts the case stops with `LV-PRC-008`, as today.
5. **Every status change is audited** with its code, as today; no content.
6. **Rollout setting** `securedoc.processing.pipeline-mode`: `inline` (today's flow, **default**) or `staged`. With `inline`, behaviour is exactly today's. With `staged`, Text/Find/Redact run as jobs. (Export keeps its own `export-mode` setting from P1.)
7. **Existing cases at upgrade:** cases in the middle of processing under `inline` finish under `inline`; switching to `staged` picks up only new work, or carries open cases over safely; say which and prove it.
8. **Screens:** the case panel shows which stage a case is at (Text, Find, Review, Redact, Exporting…), as words, using the existing chip styles.

## Prove it (the design's P2 proof)
- **Two LexaVault servers on one database** (two app instances, throwaway PostgreSQL, `pipeline-mode=staged`): 20 cases of several documents each; **no case processed twice** (no duplicate findings, redactions or exports; checked in the database and the audit), and every case finishes.
- **One server killed mid-case** (kill the process while it holds Text, Find and Redact claims): the other server finishes those cases after the claims expire; a late save from the killed worker (simulate with a stale claim number) is refused.
- The 0044 final check still runs on every redacted document; the no-redacted-value check still finds 0.
- `inline` mode: every existing test passes unchanged.
- Full backend build with the PostgreSQL tests on, `npm run test:standalone`, the no-redacted-value check, the compliance report check, `scripts/Test-LexaVault-ExportE2E.ps1` (in both modes if it can run in `staged`), the product-name guard.
- Timing on the benchmark's 60-page package in both modes (numbers only).
