## Owner's decisions on the plan's four questions

1. **Fake passwords are not committed.** Generate the test users' passwords at start-up and keep them outside the repository, under `C:\dev\lexavault\phase1-run\`. The realm file in the repository contains no passwords.
2. **Rule-based detector only** (`SECUREDOC_AI_PROVIDER=heuristic`). No run with the real model in Phase 1.
3. **Do not contact the normal `lexa-keycloak`.** For the wrong-issuer check, add a second realm inside the throwaway Keycloak and take the token from there.
4. **The UI test config may live in `frontend/securedoc-ui/`** if it cannot resolve from `test-tools/`, as a clearly named test-only file. Not needed in this sitting.

## Changes to the plan

1. **No generated secret is committed.** This covers the throwaway database password and the throwaway Keycloak admin password as well. Generate them at start-up into `C:\dev\lexavault\phase1-run\`, and have the compose file read them from there. Nothing in the repository may contain a password, even a fake one.
2. **Bind the throwaway containers to `127.0.0.1` only.**
3. **No tokens anywhere on disk.** Tokens must not be written to the results file, the logs or the console. Results record status codes and pass or fail.
4. **Build safely.** Before any `mvn clean`, check whether the normal LexaVault backend is running (port 8080 in use, or the jar under `backend\securedoc-api\target` is locked). If it is, stop and ask the owner to stop it. Do not stop it yourself. If the existing jar was built from the current commit, reuse it and skip the build.
5. **Keycloak image:** `quay.io/keycloak/keycloak:26.8.2`, the same as the running `lexa-keycloak`. Confirm with a read-only `docker inspect` if you wish.

Also confirm, before relying on it: that the `heuristic` AI provider is accepted under the profiles the plan uses. The code has an `allowHeuristic` condition in `ApplicationServiceConfig`.
