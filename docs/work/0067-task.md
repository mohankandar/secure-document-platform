# Task 0067: P3: workers that grow with the queue, the learned AI limit, intake pacing and the safety stop

Written 2026-11-24 by the LexaVault design chat. Standing rules (`QUEUE.md` rules 8, 9 and 10 apply to every queue). Report `docs/work/0067-report.md`. Owner approvals given for what this task describes, including migrations it needs (queue B uses the 07x range, queue C the 08x range; renumbered at merge if needed). No new dependency; if one is needed, stop and describe it. No redacted value is ever saved, logged or shown. Queue C (the only queue using the AI server for long runs).

Build step **P3** of the staged pipeline exactly as `claude/Staged-Pipeline-Design.md` section 6 describes (copy section 6 into `docs/work/0067-design.md` at the start so the task is self-contained):
1. **Workers per stage between a lowest and a highest**, set every few seconds from each stage's queue. Highest **measured at every start** from CPU cores and free memory (Text about one per core leaving one free; Redact about half the cores; about 0.5 GB per OCR or redaction worker, measured; Export default 4 per destination). IT's own setting always wins.
2. **AI limit learned per AI server:** go up by one while AI work waits and answers stay healthy; on 429/503 (honour Retry-After) or answers much slower than at the lower number, go back down one and remember it as the ceiling; re-check after an hour or a restart; never below 1 or above IT's maximum. Stored per AI server.
3. **Intake pacing:** watched folder and polling check less often and take fewer files per check when the queue is long; files wait at the source.
4. **Safety stop:** below 10% free disk or database space the API answers busy (`LV-INT-027`, Retry-After) and resumes above 15%; thresholds are settings; in the API contract.
5. **Admin:** per stage current/lowest/highest workers, and "AI server 1: 5 at once (learned)"; IT can set maximums.

## Prove it
Targeted tests (rule 9) for each part, with a mock AI server that refuses above a set number at once and slows down near it (the learned limit must settle at that number and drop after the mock is lowered). A load run with 400 and 4,000 small documents on one server (40,000 waits for milestone M1): workers rise to the highest and drop back, memory stays under the limit. No two-server proof needed unless claims change. One frontend run for the Admin screen.
