## What Phase 1 is

Run the R1B code for real for the first time: one login system, two entities, in an isolated environment. See `docs/design/LOGIN_CUSTOMER_ENTITY_DESIGN.md`, section 11 (points 1 to 3) and section 12 (Phase 1).

The three points to prove:

1. A person assigned to one entity cannot open the other.
2. A person assigned to both chooses one, sees only that one, and can switch.
3. The two entities run different redaction rules on the same kind of document.

In the code today an "entity" is a tenant, and the shared-login behaviour is behind the shared-issuer setting described in `docs/architecture/LEXAVAULT_R1B_TENANT_IDENTITY.md`.

## Constraints the plan must respect

1. **Isolation.** Nothing in the plan may touch the existing containers or their data (`securedoc-postgres`, `sdv-postgres`, `sdv-vault`, `lexa-keycloak`, `lexa-keycloak-db`). Use a separate throwaway PostgreSQL container on its own port, with its own name and volume, clearly labelled as Phase 1.
2. **Login system.** Use a separate throwaway Keycloak container as the stand-in for a customer's Okta, on its own port, with its own realm, groups and test users. Do not change the existing `lexa-keycloak` realm. No real passwords: test users get obviously fake ones that exist only in the throwaway container.
3. **Migration 037.** It must be applied to the throwaway database only, and it must stay out of the master changelog. Say exactly how the plan achieves that.
4. **The shared-issuer setting** is switched on for this run only, through the environment, never by changing a default.
5. **Two entities.** There is no setup command yet, so the plan may create the two tenants, their login-system records and their group-to-role mappings with a clearly labelled, test-only seed script for the throwaway database. Say which tables and rows it needs, found by reading the code and the schema, not guessed.
6. **The running dev setup.** Say whether the owner's normal local LexaVault must be stopped during the test, or whether the test instance runs beside it on other ports. Prefer whichever is simpler and safer.
7. **Repeatable.** Prefer checks that can be run again by a script (for example, getting tokens for the test users from the throwaway Keycloak and calling the API) over checks that only exist as clicks in a browser. Say which checks are scripted and which need the owner to look at a screen.
8. **Clean-up.** One command removes everything Phase 1 created and nothing else.

## What the plan must contain

1. The containers, ports, names and volumes.
2. The realm, groups and test users, and which user belongs to which entity with which role. At least: one user in entity A only, one in entity B only, one in both, and one in neither.
3. The exact list of files you would add, and where. Test-only material goes somewhere clearly separate from product code. Propose the location.
4. The step-by-step run, as commands.
5. For each of the three points: what is done, and what result counts as a pass.
6. Extra refusal checks beyond the three points, such as a forged entity choice, a user in neither entity, and a user whose entity's login-system record is not active.
7. How point 3 is shown: what differs between the two entities' redaction rules, and what document is used.
8. **Unknowns and risks.** Anything you could not determine by reading the code, and anything in R1B you expect might fail on its first real run. Be candid; a list of likely problems is more useful than a confident plan.
9. A rough size: how many files, and whether it is one sitting or several.
