## Hard rules for this run
- **Never open, print or copy anything under `C:\dev\sdv\secrets`.** Never print passwords, tokens or keys. Don't search for or guess any password.
- Don't remove, recreate or `docker compose down` the containers `securedoc-postgres`, `sdv-postgres`, `sdv-vault`, `lexa-keycloak`, `lexa-keycloak-db`. Starting or stopping them with `docker start` / `docker stop` is fine.
- **Never initialise, reset, unseal or reseal the Vault.** If Vero needs the Vault unsealed and it is sealed, **stop and ask the owner** to do it.
- Don't change Vero's code or configuration files. Use only test data and a test entity.
- Leave everything as you found it: the same containers running or stopped, LexaVault's settings back to `inline`.

## Steps
1. **Find how Vero is started on this machine** (its repo is next to this one, for example under `C:\dev\sdv`; read its README or start scripts, not its secrets). Start Vero and check its health endpoint. If it needs anything only the owner can give (a password, an unseal), stop and ask.
2. **Start LexaVault with the new export switched on:** the usual start script, with `SECUREDOC_PROCESSING_EXPORT_MODE=job` set for that run only (environment of the process, not a file). Confirm in the log that export workers started. LexaVault's SDV connection must point at the running Vero (check Admin › Integrations; the connection test must pass).
3. **A normal case:** send 3 small test cases (the existing simulator, the golden-path script or a manual upload with test PDFs). Each goes through to Vero. Check: the case shows "Exporting · ready" then "Exported"; Vero shows the submission; the audit trail shows the export job's steps.
4. **Vero down mid-run:** send 5 more cases and stop Vero while they are exporting (stop its application, not its database or Vault). Check, within a few minutes:
   - Support › Export shows Vero's destination **Paused**, with the next check time;
   - no case goes to "Waiting for you" or "Needs IT"; no attempts are used;
   - the Cases list shows "Exporting · destination paused".
   Start Vero again. Within about 5 minutes (or press **Check now**) the destination is **Working** and the 5 cases go out **in the order they were sent**. Note the times.
5. **A refusal:** cause one case to be **refused** by Vero without changing Vero. Use Vero's own API documentation to find a refusal a client can trigger with test data (for example a submission retried with different content, or a level the test entity doesn't accept). Check:
   - the case appears in **Waiting for you** under Vero's group, with "Title · LV-DLV-00x";
   - the case panel shows the yellow box, and Technical details show **"Destination code SDV-…"**;
   - **Resend this case** gives one attempt: refused again → it moves to Support › Export as a **Needs IT** group with `LV-DLV-015`.
   - If no refusal can be triggered without changing Vero, say so and skip this step.
6. **"Resend all":** if step 5 left more than one case in Waiting for you, use Resend all and check the order and the toast.
7. **Back to normal:** stop LexaVault, start it again without the job setting (`inline`), stop Vero if it was stopped before you began. Confirm the containers are as you found them.
