## 1. One list in the code

- A single registry in the domain module (for example `LvErrorCode`) holding, for each code: the code string, area, title, short description, kind, who acts, default HTTP status. Generated from or checked against `docs/work/lv-error-codes.md` by a test, so the two can never drift (same codes, same titles).
- Reserved codes (`LV-INT-027`, `LV-DLV-009`, `LV-DLV-015`) are in the registry, marked reserved, and not used yet.

## 2. Map every failure to a code

- Each inventory row listed against a code in the design gives that code. Keep today's internal identifier (enum value, `errorCode`, exception type, destination status or code) as the **detail**.
- `TechnicalFailureCode`, `IntakeRejectionCode`, the polling categories, the Scan Bridge codes, the licence reasons and the sign-in admission reasons each map to an LV code in one place.
- Anything not mapped falls back to `LV-SYS-001` and is logged with its type, so a gap is visible. A test fails if any value of those enums has no mapping.

## 3. Where the codes show

- **API error body:** add `code` (the LV code) and make `message` the code's title (plus, for `LV-CFG-001`, the field and allowed range that today's messages already give, if they hold no content). Keep `errorCode`, `correlationId`, `timestamp` as today (API version 1 compatibility). Same for the Scan Bridge's own error body. Intake warnings already carry `LV-INT-005`; keep that shape.
- **Audit trail:** every refusal, stop and export failure records `code=LV-…` and the detail. Codes only, never content.
- **Screens:**
  - Support list and Problem page, the case panel's problem text, toasts and admin screens show the title and the code (for example "Destination busy or down · LV-DLV-002"); the detail stays under Technical details.
  - The screen words for codes come from the same registry (for example a generated file the frontend reads, or an API), not a second hand-written list. Remove the screen words for codes the backend never sends (`MODEL_TIMEOUT`, `SDV_UNAVAILABLE`) once they map to LV codes.
  - Sign-in refusals: the person sees only the title (for example "No access to LexaVault · LV-AUT-002"); the exact reason stays in the log and audit for IT.
- **Watched-folder observations, polling runs, Scan Bridge items:** the LV code.

## 4. The customer error code guide (draft)

- Create `docs/api/error-codes.md`: for each code in area order, the title, what it means (the short description), who acts, and **"What to do"**: two to four plain steps for that person.
- Write the steps from what the code and the inventory row say; mark the file **"Draft: steps to be reviewed by the design chat"**. No content, names or internal hostnames in examples.
- A test that every registry code appears in the guide and every code in the guide is in the registry.
