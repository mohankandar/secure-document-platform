## Build
New redaction kinds, **switched off by default** for every entity (so nothing changes for existing setups until a Business Admin turns them on), each with a stable key, plain name and `LV-` codes where needed:
1. **Bank routing number (ABA):** 9 digits with the 3-7-1 checksum, near words such as routing / ABA / RTN, **and on the check line** (MICR: transit symbols or the routing-account-check-number pattern at the bottom of a check page).
2. **Bank account number:** 4–17 digits near account words (account, acct, a/c), and the account field of the check line; not a phone, date, amount or one of the other kinds.
3. **US tax IDs:** EIN (`NN-NNNNNNN`, with valid prefixes) and ITIN (`9NN-[70-88 / 90-92 / 94-99]-NNNN`), separate from SSN.
4. **Driver's licence and passport numbers:** keyword-anchored (licence / license / DL / passport) with plausible formats; keyword required, to keep false flags low.
- The rule "a case field or a redaction item, never both" still holds; the Business Admin's sensitive-data policy screen lists the new kinds (off) with a one-line description each.
- Confidence and review routing follow the existing rules for pattern findings.

## Prove it
- Unit tests with fake values per kind: true positives (including on OCR text with common misreads), and near-misses that must **not** match (phone numbers, amounts, dates, ZIP+4, order numbers).
- The existing detection tests pass unchanged.
- Re-run the benchmark harness (`tools/vision-benchmark`, part A, `qwen3-vl:8b-instruct`, prompt v2) with the new kinds switched on in the harness's text path: report misses and false flags per type before/after, especially **check-line routing and account numbers**. Numbers only.
- Full backend build with PostgreSQL tests on, `npm run test:standalone`, the no-redacted-value check, the compliance report check.
