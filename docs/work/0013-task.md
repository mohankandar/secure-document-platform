## Part B: plan Phases 2, 3 and 4 in one document. Change no code.

These three are small and touch the same code, so they are planned together and built in one or two tasks afterwards. Read design sections 5, 6, 8, 11 and 12, the library's `admission` package, and reports 0003 to 0012.

**Phase 2: the role mapping file and its loader** (proof: section 11 point 7, the file loads and loading it twice changes nothing).

Cover:
- The file format, with one worked example for two entities. It is written by our installers, reviewed with the customer, and kept as a record, so it must be readable by a person who is not a developer.
- Validation before anything is written: unknown role names, the platform role, unknown entities, duplicate or conflicting rows, empty groups. A bad file is refused whole, with a message naming the line. One mistyped role must never break sign-in for everyone (today it does; say exactly where and fix it in this phase).
- How it runs: an explicit command, never at server start, and never by hand-written SQL. Say how it fits with the setup command planned for Phase 5 so it is not built twice.
- What loading means: does the file replace an entity's mappings or add to them, what happens to mappings not in the file, and what is written to the audit trail.
- What goes in the library (format, parsing, validation rules) and what stays in LexaVault (writing to its tables), following the Phase 1b seam.
- Whether the product-flavoured words in the library's refusal messages are fixed here.

**Phase 3: platform access from an install-level setting** (proof: point 5, the customer's IT staff reach platform screens and nobody else does).

Cover:
- Today's state: with the shared mode on, who can reach platform screens, and why.
- The proposal: which setting names which login-system group, how it is checked on each request, and why it can never come from an entity's mapping.
- What a platform administrator can and cannot see. They must not see documents unless they also hold a role in that entity.
- How this stays correct for hosting later, where platform staff sign in through their own space.

**Phase 4: machine integrations tied to one entity, and caching** (proof: point 4, a service account for one entity cannot push into the other).

Cover:
- Today's machine admission, the weakness named in design section 8 item 7, and the fix.
- Caching on the shared-login path: what is cached, for how long, how a changed mapping or a deactivated entity takes effect, and the proof that a cached answer can never outlive a revocation by more than the stated time. Report 0012 says each request runs the lookups two or three times; remove that first.
- The preflight re-check and id conversions left from Phase 1b: remove or keep, with the reason.
