# Phase 1b plan: move the R1B login and entity code into Enterprise Identity 0.3.0

Written: 2026-11-17, from reading the code on `feature/lexavault-r1b-tenant-identity` (`3fcf5d8`), the library at `v0.2.1` (`85135a7`), and SDV on `release/vero-r7` (read-only). No code was changed.

Goal (design section 12, Phase 1b): the R1B login and entity code moves into the Enterprise Identity library as 0.3.0, and LexaVault uses it from there. SDV uses the same library in Phase 6, so the library must contain nothing that is LexaVault's own.

Proof at the end: the same tests and the same Phase 1 runtime proof (60 scripted checks and the browser script) pass.

## 2. The seam

**The library must not know about:**
- JDBC, SQL or table names;
- LexaVault's `TenantId`, `ProductRole`, capabilities, `AuthenticatedPrincipal`, audit, or `SecurityContextException`;
- Spring MVC, servlet requests, header names or `@Component`;
- LexaVault setting names.

The library's admission code needs only the JDK and the library's own types, so it goes into `enterprise-identity-core`, with no Spring. Spring-specific helpers stay in `enterprise-identity-spring` as today.

### Proposed library types

All in package `com.documentplatform.identity.admission`; no LexaVault names.

```java
record EntityId(UUID value)                                    // the product's tenant id, as the library sees it
record ConnectionKey(String providerId, URI issuer, String audience)
record AdmissionSettings(boolean sharedIssuerSelectionEnabled, boolean persistentConnections,
                         String providerId, String audience)    // built by the product from its own settings

final class IdentityAdmissionException extends RuntimeException { Reason reason(); }
enum Reason { NOT_ENABLED, NO_VERIFIED_MEMBERSHIP, AMBIGUOUS_SELECTION, NOT_AUTHORIZED_FOR_ENTITY,
              INVALID_SELECTION, NO_ROLE_FOR_ENTITY, INVALID_ROLE_GRANT, PLATFORM_ROLE_IN_ENTITY_GRANT,
              POLICY_UNAVAILABLE, MACHINE_BINDING_NOT_UNIQUE }
```

The reason codes also make the safe user messages from report 0008 possible later. The product maps every reason to its own 403 and keeps today's message texts.

### Interfaces the product implements

```java
interface ActiveEntityCandidates { Set<EntityId> find(ConnectionKey key); }
interface EntityGroupGrants      { Map<EntityId, Map<String, Set<String>>> activeGrants(ConnectionKey key); }
interface MachineEntityBindings  { Set<EntityId> find(ConnectionKey key, String clientPrincipal); }
interface EntityRoleCatalog {
    Optional<String> canonicalEntityRole(String configuredName);  // empty = unknown role, refused
    boolean isPlatformRole(String canonicalRole);                // never grantable through entity groups
}
```

### Library entry points

```java
final class EntityMembershipResolver {        // from OidcTenantMembershipResolver + TenantGroupAuthorization
  Map<EntityId, Set<String>> authorizedEntities(URI verifiedIssuer, Collection<String> verifiedGroups) }
final class EntitySelection {                 // from OidcTenantSelection + TrustedTenantAdmission
  EntityId select(String requestedEntityId, Map<EntityId, Set<String>> authorized) }
final class SharedIssuerPreflight { void requireReady(...) }   // uses EntityRoleCatalog.isPlatformRole
final class MachineEntityAdmission { EntityId requireUnique(Set<EntityId> candidates) }
```

`RequestContextResolver` keeps:
- reading the `X-Selected-Tenant-Id` header;
- normalising the token with the library normaliser, as today;
- converting `EntityId` to and from `TenantId`;
- mapping `IdentityAdmissionException` to `SecurityContextException`;
- building the principal.

**Room for later phases.** `ConnectionKey` is the single place where a customer or organization can be added for hosting (design section 8, item 12: admission must require the customer first). It is not added in 1b.

## 3. The database

- **The library owns no tables.** It defines what it needs through the four interfaces above and documents the columns a product must provide, in a schema contract page in the library README. Each product keeps its own migrations, as SDV already does for 032–034.
- **Why not a shared library changelog:**
  - the grants table points at each product's own entity table;
  - the products number their migrations differently (LexaVault XML 032–037, SDV SQL 014–016);
  - the design requires a separate, reviewed schema step per install (section 6, Phase 5b).
- **The rule that the server inserts nothing at start is unaffected** by the move. `OidcConnectionBootstrap` stays in LexaVault and is removed in Phase 5 (item C).
- **Migration 037 stays out of the master changelog.** The Phase 1 proof keeps applying it through `test-tools/phase1-shared-issuer/db/phase1-changelog.xml`, and `SharedIssuerMigration037ContractTest` stays unchanged to guard this.

**Disagreement.** Design section 8 lists "customer and entity records, and the rule that ties them together" as library content. The library README says "Persistence and product authorization remain product-owned." I read the design as the record *types and rules* in the library and the *persistence* in each product. Question 2 asks the owner to confirm.

## 4. Settings

- **Today:**
  - `securedoc.security.oidc.*`, bound by LexaVault's `SecurityProperties`;
  - the shared-issuer flag is also read a second time by `JdbcOidcConnectionBindingRepository` through `@Value`, with default `false` in both places.
  - SDV uses its own names.
- **Proposal: the library gets no setting names of its own.** It takes an `AdmissionSettings` object, which each product builds from its own settings. LexaVault keeps `securedoc.security.oidc.shared-issuer-tenant-selection-enabled` (default `false`), so nothing is renamed and no old name has to keep working.
- This keeps the library free of Spring Boot, which it does not use today.
- **Later option, not proposed now:** if a shared name is wanted, a Spring Boot module could read `enterprise-identity.oidc.shared-issuer-selection-enabled` with a fallback such as `${enterprise-identity.oidc.shared-issuer-selection-enabled:${securedoc.security.oidc.shared-issuer-tenant-selection-enabled:false}}`. The default stays off.
- **The design document gives no setting names**, so there is no disagreement here.

## 5. The frontend

**Recommendation: it stays in LexaVault until SDV needs it (Phase 6).**

The browser-side entity code is:
- `src/api/tenantContext.ts`, the selection and its revision;
- the race guard in `src/api/client.ts`;
- the chooser and `enterTenant` / `listSwitchableTenants` in `App.tsx`;
- `src/studio/EntitySwitch.tsx`;
- `src/api/pendingWork.ts`.

Reasons to keep it in LexaVault for now:
- **SDV's UI would not take it as it is.** It uses React 18 and Vite like LexaVault, but different versions (Vite 5.4 against 6.4, lucide 1.x against 0.460), no SWR, no router dependency, and its own `auth.ts`. A shared package would have to be written for both apps.
- **There is no package infrastructure.** No npm registry or workspace exists for the library, and adding one is new infrastructure.
- **The code is small and has just settled** (tasks 0008 and 0009). It is better proven in one app first.
- **The design rule on browser input sits on the server.** The server revalidates the selection on every request, so the browser code is not a security boundary. A second copy in SDV would be a UX duplicate, not a security risk.

For Phase 6, write down the browser contract now, so SDV matches it:
- the header `X-Selected-Tenant-Id`;
- `GET /me/tenants`;
- the rules: discard responses after a switch, clear the selection on sign-out, and never treat the selection as authority.

## 7. Risks and the frozen areas

### What changes in the frozen areas, and why

| Frozen area | What changes | Why | What does not change |
|---|---|---|---|
| Enterprise Identity R1 (the library and the identity administration) | Library: new `admission` package and new tests; version 0.3.0. LexaVault: `TrustedActorResolver` replaced by the library's equivalent (P3), and the duplicate audience validator removed (P4). | This is Phase 1b's goal. P3 and P4 remove copies of library code. | The 11 existing library classes' behaviour, connection activation, rollback and recovery, `OidcTenantResolver`, `JdbcOidcConnectionBindingRepository` and the admin screens |
| OIDC session continuity | **Nothing** | 1b is backend only | Browser sign-in, refresh and sign-out |

### Risks

1. **Behaviour drift during the move.**
   - *Mitigation:* the P1 parity test runs both implementations side by side; the moved tests keep every case; `RequestContextResolverSecurityTest` and the Phase 1 proof stay unchanged.
   - Message texts are kept identical, because some tests check them.
2. **Actor ids.** A different UUID would split one person into two in the audit trail.
   - *Mitigation:* P3 is its own step, with an identical-output test.
3. **The library becoming LexaVault-shaped.** *Mitigation:* the forbidden-names rule in section 2, plus a library test that fails if any `com.securedoc` import appears.

### Open library findings

All are pinned by tests in L0; whether to change them is question 5.

| Finding | What happens today | Exposure |
|---|---|---|
| Groups claim over 200 values, or a value over 200 characters | `IdentityClaims.values` throws `IllegalArgumentException`. LexaVault turns it into **403** (`RequestContextResolver.normalizeIdentity`); SDV turns it into **401** (`EnterpriseJwtAuthenticationConverter`). | Not a 500 in either product today. Any new caller that does not catch it would give 500. The two products already answer differently. |
| Token with no `sub` | `OidcJwtIdentityNormalizer` throws `IllegalArgumentException`: LexaVault 403 (and `TrustedActorResolver` also refuses), SDV 401 | Same as above |
| Plain-string groups claim | Split on spaces and commas, so "Business Users" becomes two groups | Keycloak and Okta send arrays, so this is theoretical today. A provider sending one string would mis-match groups. |
| Trailing slash on the issuer | The library's caching resolver and LexaVault's `findActive` strip it; the R1B candidate, grant and machine lookups use the raw `iss` | A token `iss` with a trailing slash would pass legacy lookup but fail shared-issuer admission (fails closed). `ConnectionKey` can normalise in one place, but that is a behaviour change. |
| The library has tests only for the audience validator | — | L0 adds them before anything moves |

## 8. What SDV will need in Phase 6 (describe only)

- **Adapters.** The four interfaces implemented on SDV's own tables: candidates and machine bindings on its `enterprise_identity_connections` (already present, 014–016), plus a grants table equivalent to 036, and 037's index change, as SDV migrations.
- **An SDV role catalogue** naming SDV's roles and its platform role.
- **Exception mapping.** `IdentityAdmissionException` mapped in SDV's security layer. SDV answers 401 for claim errors today, against LexaVault's 403, so the two products should agree on one status per reason.
- **The selection contract** (section 5): header, `/me/tenants`, server revalidation on every request. SDV's UI then needs a chooser and a switch: either its own, or by then a shared package.
- **Settings.** SDV builds `AdmissionSettings` from its own setting names, with shared-issuer off by default.
- **SDV's duplicate `JdbcOidcConnectionBindingRepository`.** A shared JDBC module with configurable table names could replace both copies later. Nothing in 1b blocks that or has to be redone for it.
- **Nothing in 1b assumes LexaVault's names**, so SDV adds code; it changes no library code. The one thing to decide before Phase 6 is the shared status codes (401 or 403 per reason).

## Where the code and the design disagree

1. **Design section 8 vs Phase 1b.** Section 8 lists for the library things that do not exist yet: customer records, the mapping-file loader, the setup command core and the licence check. Phase 1b (section 12) moves only existing R1B code. This plan follows section 12; the new pieces are built in the library in Phases 2–5.
2. **Records vs persistence.** Design section 8 ("customer and entity records … go into the shared library") against the library README ("Persistence … remains product-owned"). See section 3 and question 2.
3. **"The same tests pass unchanged"** (section 12 proof) cannot hold literally for the six tests whose classes move, because their imports and types change. See question 1.
4. **Item C and the server-start rule.** The design says the server inserts nothing at start (section 6); the code still does, through `OidcConnectionBootstrap`. 1b leaves it in LexaVault, unchanged; it is removed in Phase 5.
