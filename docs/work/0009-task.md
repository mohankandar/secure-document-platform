## Part C: the entity switch in the newest design (branch `feature/entity-switch` from the feature branch)

The newest (Case File) design has the chooser at sign-in but no way to change entity afterwards. The older sidebar has one. The design requires switching inside the app.

Behaviour:

1. The entity name at the top right becomes the switch, only for a person with two or more entities. A person with one entity sees the name as plain text, as now.
2. Opening it lists the person's entities, read fresh from the server, with the current one marked.
3. Choosing another entity:
   - asks for confirmation first if there is unsaved or in-progress work on screen;
   - leaves nothing from the previous entity on screen or in memory (packages, documents, findings, policy, counts, cached responses);
   - reloads the person's roles and capabilities, since they can differ per entity;
   - lands on the workspace home of the new entity.
4. If the server refuses the choice, the person stays where they are and sees a plain message.
5. It works by keyboard and has a proper accessible name.

Rules:

- Reuse the older sidebar's switch logic. Do not write a second implementation of the same thing.
- Do not weaken the API client's race guard or the server's revalidation of the selected entity on every request.
- No backend change. If one seems needed, stop and report.
- Say in the report how the previous entity's data is cleared, and why that way is reliable.

Tests first, in the style of `test:oidc-signin`:

- two entities: switch from A to B shows only B's data and B's roles;
- a request still in flight during the switch is discarded, not shown;
- one entity: no switch control;
- a refused choice leaves the person on the current entity.

Then verify on Phase 1: extend the browser script so `carol.ab` switches A to B and back without signing out, and rerun the 60 checks.

Commit on `feature/entity-switch` and push it for review. Do not merge. Leave the Phase 1 environment running on port 15173 with the switch, for the owner to try.
