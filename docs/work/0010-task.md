## Part B: plan Phase 1b. Write a plan, change no code.

Goal (design document, section 12): move the R1B login and entity code out of LexaVault into the Enterprise Identity library as version 0.3.0. LexaVault then uses it from the library. SDV will use the same library in Phase 6, so the library must not depend on anything that is LexaVault's own.

Proof required at the end of Phase 1b: the same tests and the same Phase 1 runtime proof (60 scripted checks, the browser script) pass unchanged.

The plan must cover:

1. **Inventory.** Every R1B class, interface, migration, setting and test involved in sign-in, entity admission, entity selection, group grants and machine admission. For each: where it lives now, and whether it moves to the library, stays in LexaVault, or splits. Give the reason for each "stays" and "splits".
2. **The seam.** What the library needs from the product and must not know about (database access, table names, product roles, capabilities, audit, web framework pieces). Propose the interfaces the product implements. Keep the library free of LexaVault names.
3. **The database.** Which tables are the library's concern and which are the product's. How migrations are owned when two products use the same library, given the rule that schema is a separate step and nothing is inserted at server start. Migration 037 stays out of the master changelog.
4. **Settings.** Today's setting names are `securedoc.*`. Propose library names and how the old names keep working, with shared-issuer selection still off by default.
5. **The frontend.** Whether any of the browser-side entity code (chooser, switch, tenant context, race guard) should become shared now, or stay in LexaVault until SDV needs it. Recommend one, with the reason.
6. **Order of work.** Small steps, each one building and passing all tests before the next, with a commit per step. Say where the Phase 1 proof is rerun.
7. **Risks and the frozen areas.** This touches Enterprise Identity R1 and OIDC session continuity, both frozen. List exactly what in the frozen areas must change and why. Include the open library findings: possible 500s for a groups claim over 200 values or a value over 200 characters, a token with no `sub`, a plain-string groups claim split on spaces and commas, the trailing-slash issuer difference between the library and LexaVault's lookups, and the library having tests only for the audience validator.
8. **What SDV will need** in Phase 6, so that nothing in 1b has to be redone. Describe only.
9. **Size.** An honest estimate in sittings, and which steps could run in a second working folder at the same time as other work.
