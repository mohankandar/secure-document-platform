## Goal
Prove the whole P1 export path works on a running LexaVault with `securedoc.processing.export-mode=job`, using the **folder (file system) destination** as the real destination. "Down" is simulated by making the destination folder unreachable (rename it away or point it at a path that does not exist), "up" by putting it back. No SDV/Vero involved.

## Scenarios (each a marked integration test, tag `e2e-export`, skipped in the normal build)
1. **Happy path:** 3 cases finish; each export job reaches DONE; the files are in the folder; the case says "Exported"; audit records present.
2. **Destination down, health check fails:** take the folder away, finish 3 cases. The destination is **paused**, no attempts are spent, cases show "Exporting · destination paused", one IT alert "LexaVault can't reach its destinations" if it is the only destination. Put the folder back: the probe (shorten the 5-minute interval with a test setting) resumes it and the cases export **in the order they finished**.
3. **One case fails while the destination is healthy:** make one case's write fail (for example a read-only target file name for that case only, or a test hook already in the code; say which). That case follows its own schedule (shortened), gets one rebuild before the 3rd retry, then lands in **Needs IT**; the other cases are not held up.
4. **Backup rule:** 3 different cases failing within 10 minutes pauses the destination even if the health check passes.
5. **IT queue:** grouped alert with "Retry all" works; "Resend all" per destination (needs `EXPORT_RESEND`; check a Processor and a Supervisor can, a Reviewer cannot).
6. **Restart in the middle:** stop the app while jobs are WAITING_RETRY or PAUSED, start it again: nothing lost, nothing sent twice.
7. **Retention:** a resent case uses the copy kept for that destination; after the retention window (shortened) the copy is gone and resend says so clearly.
