`.\Start-LexaVault-OIDC.ps1 -IssuerUri http://localhost:8181/realms/document-platform-local -Audience lexavault-api -ScannerMode SIMULATOR -AiModel qwen3.5:9b` on the owner's existing database (`securedoc-postgres`, data from before 0037):

- The demo step then failed: `duplicate key value violates unique constraint "tenants_slug_key"`, `Key (slug)=(local-demo) already exists` (the old `0000…0001` demo entity). `DEMO_STEP_FAILED`, exit 1. The app never started.

## Fix
1. **Existing databases work.** The start path must succeed on a database that already has pre-0037 data, without changing or deleting that data. The new demo entity must not clash with the old one (slug, name or any other unique value); choose how and say why. The old entity stays usable.
2. **"Fresh" means the demo step hasn't run,** not "no customer stored". Setup and the demo step are both safe to re-run: on the owner's database as it is now (setup already applied, demo step failed half-way) the next start must finish: setup "0 created … unchanged", demo step completes, app starts.
3. **OIDC start signs in through the Keycloak issuer it was given.** In OIDC mode the login connection used for sign-in must be the one for `-IssuerUri` / `-Audience` (Keycloak), not the demo files' `demo-okta` placeholder. Check how the demo files and the OIDC start script should combine, and make `Start-LexaVault-OIDC.ps1` work in one command on both a fresh and an existing database. (Platform-core's setup only takes https issuers; you said the demo step sets up the local Keycloak connection. Make that true for this path too.)
4. **Platform identity schema:** platform-core now has identity **V2** (P029, client bindings; a V1-only database is refused). If the build you pin to includes it, the schema step must run V2; say which platform-core commit you used.
