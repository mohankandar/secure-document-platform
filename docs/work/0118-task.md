1. **Meaning in the schema itself.** One new Liquibase changelog that sets `remarks` (COMMENT ON TABLE / COLUMN) for every LexaVault table and column: one plain sentence each (what it holds, what it is used for). Draft them from the code (entities, repositories, the changelogs' history). Mark any you are unsure of with "(to confirm)" and list them in the report for the owner. 2. **Generated dictionary.** A script (test-tools or scripts) starts a throwaway PostgreSQL, runs all migrations, reads the live schema (information_schema + pg_catalog comments) and writes `docs/data/DATA-DICTIONARY.md`: per table its purpose, columns (name, type, required, default, meaning), primary key, foreign keys and indexes; plus **retired tables** (dropped by later migrations, e.g. `business_record_identifiers`) with what replaced them. It also writes `docs/data/RELATIONSHIPS.md` with a Mermaid diagram of the main links (cases, documents, findings, case fields `fld_record`/`fld_value`, pipeline jobs, audit records, exports).
3. **CI keeps it true.** A CI step regenerates the dictionary and fails if (a) any table or column has no comment, or (b) the committed dictionary differs from the generated one ("run <script> and commit").
4. **Everyone reads it.** Add to the repository's `CLAUDE.md`: "Before writing SQL, a query for the owner, or a migration: read docs/data/DATA-DICTIONARY.md. Every new table or column needs a comment in its changelog." Add a section "Useful queries" at the end of the dictionary: find a case by contract or member number (the join used by JdbcCasePrimaryIdentifierLookup), time per stage for a case (pipeline_jobs), whole-case time (audit_records), findings by kind and how they were placed (0105 columns).
5. Only comments change in the database: no table, column, type or data change.

Proof: migrations run on a throwaway PostgreSQL; the CI check fails when a column without a comment is added (show it in a test or the report), passes on the real branch.
