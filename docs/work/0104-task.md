# Task 0104: One case per contract, documents with versions, never refuse a business resend

Written 2026-11-26 by the LexaVault design chat. Queue C, **HELD until the owner starts work on 2026-11-27**. Standing rules (`QUEUE.md` rules 8–11). Report `docs/work/0104-report.md`. Migrations 08x. **Design first:** write `docs/design/CASE_VERSIONS.md`, decide its open points as recommended (list them in the report), then build. No new dependency.

## Why (owner, 2026-11-26; a defect and a task)
Contract files arrive in pieces and get corrected. Today a second batch or a corrected document for the same contract is refused or ignored ("Already received", or a case-field conflict). **LexaVault must not refuse a business resend.** Customers pay by page, so nothing unchanged is processed twice. Owner's examples:
1. A contract has 6 documents: 3 arrive, the other 3 arrive 15 days later.
2. Quality control finds a mistake; the customer re-signs document 3; it arrives after 45 days.
3. Pages were missed when scanning; the whole document is scanned again.
4. An updated document comes from an e-signing or e-vault system (DocuSign, eOriginal) into the watched folder.

## The rules (owner chose option 1)
1. **The case is the contract.** A new arrival whose case fields match an open case **joins that case** as a new batch (watched folder, API, polling, scan). Each batch is processed, reviewed and delivered as it arrives, never held for the rest.
2. **Each incoming file is one of three:**
   - **identical** to a document the case already has (same bytes): skipped, recorded, **not processed or counted again**;
   - **new document**: added;
   - **new version of an existing document**: becomes version N+1; processed and reviewed in full; delivered marked "replaces version N". Old versions are **never overwritten or merged page by page**; they stay in the case history until retention removes them and are never delivered again.
3. **How a new version is recognised, without reading the document's text** (in this order):
   a. the source says so: the API's document ID; in a manifest, `documentId` or `replaces`; at a scan, the operator picks "new document" or "replaces …" from the case's list;
   b. the file's own identity: the PDF's permanent document ID (trailer `/ID`, first part), the XMP `DocumentID`, an e-signing envelope or document ID that the system stores in the file's properties, or an **incremental update** (the new file begins with the old file's bytes, as a re-signed PDF often does);
   c. **still unclear** (same file name, different content, no ID): added as a new document and marked "possible new version of …"; a person can link it in the case at any time. **Never blocks or refuses the batch.**
   Check what DocuSign and eOriginal really put in their files (public sample files or their documentation) and record it in the design doc; don't assume.
4. **Unchanged pages of a new version:** where a page is byte-for-byte the same as in the previous version (incremental update, or the same page image), reuse that page's reviewed redaction decisions so the reviewer sees only what changed. The whole new version is still checked by the final guard (0099) before delivery.
5. **Delivery:** each batch is a delivery cycle (the existing export cycles) with, for each document, its version and what it replaces, so Vero or an export folder can swap the old copy.
6. **Which cases take new batches:** any case not rejected and not erased. A batch for a rejected or erased case: a new case for the same contract (owner can change this later).
7. **Billing and reports:** pages are counted once per version processed; skipped identical files count zero. Reports show batches, versions and skipped files per case.

## Owner's clarification (2026-11-26 15:20)
- **No time limit:** a document arriving 6 months later (or any time) for an open case is a new version and is processed; the business decides what to do with it.
- **The only thing not taken again is an exact copy:** same bytes as a document already in the case (a SHA-256 of the file content alone; the file name and folder name don't matter). Any change at all, even a re-save or a changed date inside the file, makes it a new version.

## Owner's clarification (2026-11-26 15:22)
- **Downstream keeps every version.** Vero does not replace version 1; it keeps version 2 next to it so the history of changes is visible. Delivery sends each new version as an addition (its version number and the version before it), never as an overwrite. Send only what changed in a batch (the skipped identical documents are not sent again).
- **One case per contract, with its full history in LexaVault:** for every batch, the date, the source, and per file whether it was processed (and as which version) or skipped as an exact copy. Example: day 1, 5 documents processed (each v1); day 2, 4 skipped, 1 processed as v2; 6 months later, 1 processed as v3. Shown on the case and in Reports.
- **Fingerprints are kept for the life of the case**, including after retention purges an original file, so a file arriving months later is still compared against every version ever received. (A fingerprint is a hash of the file, not its content.)
- **Page-image comparison:** a page that renders exactly like the same page of the previous version reuses that page's review decisions (covers a sender that re-exports all files with new internal dates); the final guard still checks the whole file.

## Owner's additions (2026-11-26 15:24)
- **Never into the wrong case:** a batch joins a case only when **all** its key case fields match (contract and member number, and any other primary or required identifying field). One matching and another not: the batch goes to a person to decide, never merged. Wrong-case filing is a privacy breach.
- **New versions are visible:** a case that receives a new version after delivery shows a "New version" badge on the dashboard and in Reports; an optional notification to the entity's team (through the existing notifications).
- **Reuse only when nothing else changed:** page decisions are reused only if the entity's redaction settings (and the model versions) are the same as when the earlier version was reviewed; otherwise the new version is checked in full.
- **Retention of an open case:** its retention period runs from its **last delivery**, so each new version gets its full period.
- Not now (owner): a page-by-page "what changed" view, and savings figures in Reports.
