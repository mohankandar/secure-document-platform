## Owner's rule (2026-11-26)
**LexaVault finds and covers by itself. Sending a finding to a person is the worst case, not the normal path.** Every time a person has to place a box, LexaVault has failed and the report must say why.

## The measured problem (owner's run 2, 2026-11-26)
115 findings: 103 fully automatic; **12 found but "Location unknown"**, so the owner had to drag a box for each (audit: 12 `FINDING_BOUNDING_BOX_UPDATED` + 12 `FINDING_CONFIRMED`); 0 drawn from scratch. The 12 are mostly on handwritten and scanned pages read by the vision model, which names the value but gives no usable place. Cases 779001127009–016 in the owner's local database; files in `C:\dev\lexavault\test-pdfs` (watched-drops-run2).

## Steps
1. **Measure first:** for each of the 12, which kind, which page type (handwritten, scan, photo, form field), which reader found it, and why no place was found. Table in the report.
2. **Place the value automatically**, in this order, until one works:
   a. ask the vision model for the value's box (a box in page coordinates in the answer schema), checked: the box must lie on the page and its OCR or image content must be plausible for the value;
   b. find the value's text in the page's OCR words (with OCR's usual confusions: `0/O`, `1/l`, spaces, dashes) and use those words' boxes;
   c. find the value's label or neighbour (e.g. "DOB", "Social Security No.") and take the field area to its right or below, as a form line;
   d. only when none works: cover generously (the whole line or field area) **and** send it to a person, saying which step failed.
3. **Form fields and annotations:** their place is known from the PDF itself (field rectangle, annotation rectangle); never "Location unknown".
4. **Re-run run 2** (the owner's files, plus `long-*`) through the product: target **0 findings without a place** on typed and scanned pages, and as few as possible on handwritten pages, every remaining one listed with its reason. No new leak; the final guard (0099) still runs.
