## What the code does today (checked by the design chat)

- `audit_records` columns: id, tenant_id, actor_id, action, resource_type, resource_id, outcome, correlation_id, detail, occurred_at, created_at. There is no display name and no case ID.
- `AuditService` has `recordSuccess`, `recordFailure` and `recordDenied`, with about 118 call sites.
- `AuthenticatedPrincipal` holds actorId, tenantId, username and roles. The sign-in side already reads a display name claim (`SecurityProperties.displayNameClaim`, default `name`, used in `SecurityConfig`).
- `SENSITIVE_DATA_POLICY_CHANGED` detail today: `Sensitive-data policy changed: enabledCount=4, threshold=0.85, reviewMode=UNCERTAIN_ONLY, maskSsnLastFour=true`. It holds no type names, no preset and no previous values.
- The Admin › Audit trail UI reads `threshold=` from the detail with a regex (`studio/admin/auditRules.ts`, `changeLine`). It shows `actorId`.
- `ReviewMode` is `UNCERTAIN_ONLY` or `REVIEW_ALL`.

## Steps

**A1. Actor display name and case ID, recorded at the time of the action.**
- Don't change the ~118 call sites. Give `AuditService` a small request-scoped source for the current person's display name, in the application layer, filled where the request's principal is resolved. Use the display name claim, or the username when there is none.
- Work done by the system (worker, schedulers, `SYSTEM_ACTOR_ID`) records no display name. The UI already treats the system actor separately.
- **Case ID:** use the same case identifier the Cases page shows. Record it on records whose resource is a case (package) or something inside one (document, finding, artifact), when it can be found without an extra query per record. Otherwise leave it empty.
  - If that identifier is a business identifier such as a loan number, stop and ask before recording it.
- Expose both on the audit API response and the export (JSON and CSV) as new fields. Existing fields stay unchanged.

**A2. Migration `040-audit-actor-name-case-id.xml`**, registered after 039. It adds two nullable columns to `audit_records`: `actor_display_name` (VARCHAR 200) and `case_id` (VARCHAR 100). Old records are never changed: no backfill. Run it on a throwaway database only, never against `securedoc-postgres`.

**A3. Policy changes record the type names, the preset and the previous values.**
- Keep the existing keys, their order and their format, so `auditRules.ts` keeps working. Append the new keys after them:
  - `enabledTypes=` the type names, sorted, comma-separated, for example `CREDIT_CARD_NUMBER,DATE_OF_BIRTH,SSN`;
  - `preset=` worked out **on the server** from the saved values, never sent by the browser:
    - `STRICT` when the review mode is `REVIEW_ALL`;
    - `BALANCED` when it is `UNCERTAIN_ONLY` at 0.80;
    - `LIGHT` when it is `UNCERTAIN_ONLY` at 0.70;
    - `CUSTOM` otherwise;
  - `previous=` the same keys for the policy before the change, in brackets; `previous=none` when there was none.
- Add one shared helper for the preset rule, with tests, so U023 and the compliance report use the same rule later.
- Type names are category names, not values. Check that nothing else is added.

**A4. New audit action `COMPLIANCE_REPORT_CREATED`.**
