## Part B: the failure inventory (no code changes)

**Why:** the owner wants every failure a customer can meet to have a stable code `LV-<AREA>-<NNN>`, a plain message, and a short description, with the steps in a separate error code guide (FAQ page or PDF) so customers don't need to call support. Reports' "Needs attention, by reason" will show these codes. The design chat designs the code list from this inventory; **do not assign the final codes yourself**, only propose an area.

**Find every place LexaVault fails, refuses or stops something**, across all modules (domain, application, infrastructure, api, scan-bridge, ai, worker) and the frontend's error messages. At least:
- intake refusals (push API, polling, scanner, watched folder, manual upload): every 4xx and its error code or message;
- processing stops: every `TechnicalFailureCode` value and where it is raised, plus any stop that does not use one;
- AI / model failures (Ollama, OpenAI-compatible, the inference pool);
- redaction and PDF failures;
- review and approval refusals (four-eyes, state conflicts);
- export / delivery failures: full case and split, every adapter, every retry path, 409 handling;
- sign-in, tenant and permission refusals (403 / `AUTHORIZATION_FAILED`, entity chooser cases);
- configuration and admin validation errors (policy, connections, watched folder, destinations);
- start-up and health failures an IT Admin would see;
- the two codes already in use: `LV-INT-005` and `LV-DLV-003`.

**For each one, one row in `docs/work/0022-failure-inventory.md`:**

| Column | What to put |
|---|---|
| # | running number |
| Where | module and class / method (file path) |
| Trigger | what causes it, in plain words |
| Today's identifier | enum value, error code string, exception type, or "none" |
| HTTP status | if it is an API response |
| What the person sees today | exact message text, and on which screen or response (Support, case panel, toast, API body, log only) |
| Recorded in | audit action, log, both, neither |
| Retried today? | no / immediately N times / other |
| Who can act | source system, reviewer, Business Admin, IT Admin, nobody |
| Proposed area | INT, PRC, AI, RED, REV, DLV, AUT, CFG, SCN, SYS (or suggest another) |
| Notes | duplicates, messages that leak content (flag them), messages that are unclear |

Rules:
- **Never put a redacted value, a file name, a person's name, or any secret in the inventory.** Describe messages that would contain such values instead of copying an example.
- Flag in a separate section any message that **can show content or a secret** today. That is a bug list for the design chat, not something to fix here.
- Flag places that fail **silently** (caught and only logged, or swallowed).
- Group rows by proposed area, then by where.
- End with counts per area and a short list of the top 10 failures a customer is most likely to meet, with your reason.
