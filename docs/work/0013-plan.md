# Plan: Phases 2, 3 and 4 together (role mapping file, platform access, machine integrations and caching)

Written: 2026-11-17, from the code on `feature/lexavault-r1b-tenant-identity` (`992403a`), Enterprise Identity `v0.3.0`, design sections 5, 6, 8, 11 and 12, and reports 0003 to 0012. No code was changed.

All three phases touch the same request path: `RequestContextResolver`, `OidcTenantMembershipResolver`, the library's `admission` package and the three JDBC lookups. So they are planned as one piece of work, and built in two tasks (section 5).

## 1. Phase 2: the role mapping file and its loader

Proof: section 11 point 7. The file loads, and loading it twice changes nothing.

### 1.1 Today

- **How grants are made:** the group-to-role grants live in `tenant_oidc_group_grants` (migration 036). Nothing in the product writes them; today they exist only through hand-written SQL, such as the Phase 1 seed.
- **One mistyped role breaks sign-in for everyone.** This happens in `JdbcTenantOidcGroupGrantRepository.activeGrants` (`securedoc-infrastructure/.../identity/JdbcTenantOidcGroupGrantRepository.java`, the role check inside the row callback). One row with an unknown or platform role throws `IllegalStateException` for the whole lookup. The lookup covers every entity on that login system, so every person on it gets 409 on every request.
- **The library has the same problem at a smaller scale.** `EntityGroupAuthorization.authorizedRoles` refuses the whole request when a matched grant names an unknown role. A person in A (bad row) and B (good) loses B too.

### 1.2 The file format

**A CSV file, one row per grant.** It opens in Excel or any text editor, an installer can review it with the customer line by line, and the JDK reads it without a new dependency.

```csv
# LexaVault role mapping file. Format: lexavault-role-mapping/1
# Customer: Acme Mortgage. Reviewed with Jane Doe (Acme IT) on 2026-12-01.
# Login system: Acme Okta, issuer https://acme.okta.com/oauth2/default
# Lines starting with # are comments. One row per group and role.
entity_id,entity_name,group,role
a1a1a1a1-0000-4000-8000-00000000000a,Acme Lending,Lending-Processors,DOCUMENT_PROCESSOR
a1a1a1a1-0000-4000-8000-00000000000a,Acme Lending,Lending-Supervisors,DOCUMENT_SUPERVISOR
a1a1a1a1-0000-4000-8000-00000000000a,Acme Lending,Lending-Admins,BUSINESS_ADMIN
a1a1a1a1-0000-4000-8000-00000000000a,Acme Lending,Acme-IT,TENANT_IT_ADMIN
b2b2b2b2-0000-4000-8000-00000000000b,Acme Servicing,Servicing-Staff,DOCUMENT_SUPERVISOR
b2b2b2b2-0000-4000-8000-00000000000b,Acme Servicing,Servicing-Reports,REPORT_VIEWER
b2b2b2b2-0000-4000-8000-00000000000b,Acme Servicing,Acme-IT,TENANT_IT_ADMIN
```

- **`entity_name` must match** the entity's name in the product. It is there so a person reading the file knows which entity each row belongs to.
- **The first non-comment line must be the header** exactly. The `Format:` comment is not checked in format version 1.
- **Group names are case-sensitive and written exactly as the login system sends them.** The file must not use Keycloak's full-path form `/group`.
- **The issuer comes from each entity's ACTIVE login-system record**, not from the file, so it is never written twice.

### 1.3 Validation before anything is written

The whole file is read and checked first. Any error refuses the whole file, and nothing is written. Each message names the line, for example: `line 6: unknown role "DOCUMENT_PROCESOR"`.

| Check | Refused when |
|---|---|
| Header | missing, or not exactly `entity_id,entity_name,group,role` |
| Each row | wrong number of columns; blank entity id, group or role; entity id not a UUID |
| Role | not a role the product knows (`EntityRoleCatalog.canonicalEntityRole` is empty) |
| Platform role | the role is the platform role (`isPlatformRole`): platform access never comes from this file (Phase 3) |
| Entity | not an ACTIVE entity in the product, or the name differs from the product's name for that id |
| Login system | the entity has no ACTIVE login-system record (its grants could never apply) |
| Duplicates | the same entity, group and role twice |
| Conflicting names | one entity id with two different names in the file |
| Empty entity | an entity's only rows leave it without any role; that case cannot occur, because an entity appears only through its rows |
| Group | blank, longer than 200 characters (the library's claim limit), or containing a comma or a line break |

### 1.4 Loading: what it means

- **The file is the complete record for every entity it names.** For those entities the loader makes the grants exactly equal to the file: it adds rows that are missing and removes rows that are not in the file.
- **Entities not in the file are not touched.**
- **One transaction.** The comparison and the writes run in one database transaction; either all of the file applies, or none of it does.
- **Loading twice changes nothing.** The loader works out the difference first. A second load of the same file finds no difference, writes nothing, records nothing in the audit trail, and reports `no changes`.
- **Audit trail:** one `ROLE_MAPPING_LOADED` record per entity that changed (a new audit action). It holds:
  - the counts added and removed;
  - the file's SHA-256;
  - the file name;
  - the operating-system user who ran the command.
  
  The actor is the system actor, as for other system actions, because no person signs in to run the command.
- **The command prints a summary per entity** (added, removed, unchanged) and exits 0. On a refused file it prints every error and exits non-zero.

### 1.5 How it runs

- **An explicit command, never at server start and never as hand-written SQL.** The backend jar gets a command mode:
  `java -jar securedoc-api.jar --lexavault.command=load-role-mappings --file=<path>`.
  This starts Spring without the web server, runs the command and exits. It uses the same database settings as the server.
- **Phase 5 uses the same entry point.** The setup command (`--lexavault.command=setup --file=<answers file>`) becomes a second command on it, and the setup command calls the role-mapping loader for the mapping part of an install. So there is one command runner and one loader, built once.
- **It never changes the schema.** It only writes rows, as the design requires.
- **The Phase 1 seed stops inserting grants by SQL.** It loads a test-only mapping file through the command instead. That proves the loader on every Phase 1 run.

### 1.6 What goes where (the Phase 1b seam)

| Library (Enterprise Identity 0.4.0) | LexaVault |
|---|---|
| The file format: parsing CSV with line numbers, and the header rule | The command runner (`--lexavault.command`) |
| The validation rules in 1.3 that need no database: syntax, roles through `EntityRoleCatalog`, the platform role, duplicates, conflicting names, group limits | The checks that need its tables: the entity exists and is ACTIVE, the name matches, an ACTIVE login-system record exists. The library asks for these through a small interface, `MappingTargets` |
| The difference between file and store (`MappingPlan`: per entity, rows to add and remove) | Reading and writing `tenant_oidc_group_grants` in one transaction, and the audit records |

The library still owns no tables.

### 1.7 Fixing "one mistyped role breaks sign-in for everyone"

- **The loader can no longer write a bad role.**
- **A row written by hand can still be bad**, so the read path changes too:
  - **LexaVault adapter:** the read no longer throws for the whole lookup. An invalid row is returned to the library as it is, and an ERROR is logged naming the entity and the row.
  - **Library:** `EntityMembershipResolver` treats an entity whose matched grants are invalid as not admissible. That entity is refused, and it is logged with reason `INVALID_ROLE_GRANT`. The person's other entities still work, and other people are unaffected.
- **It is still fail closed for the broken entity**: nobody enters it until the row is fixed.
- **This changes behaviour in the library** (0.3.0 refuses the whole request). It is covered by tests, and by Phase 1 check M-08.

### 1.8 The library's product words

These are fixed in Phase 2, because Phase 2 releases a new library version anyway.
- **Library:** the messages become neutral ("entity", "platform role"). The `Reason` codes are unchanged.
- **LexaVault:** `IdentityAdmissionMapping` maps each `Reason` to LexaVault's own message, with the **current texts**. So LexaVault's 403 texts stay identical, and the P2a resolver tests, which assert those texts, pass unedited.

## 2. Phase 3: platform access from an install-level setting

Proof: section 11 point 5. The customer's IT staff reach platform screens, and nobody else does.

### 2.1 Today

- **What the platform role grants.** `PLATFORM_OPERATIONS_ADMIN` gives `PLATFORM_OPERATIONS`, `PLATFORM_DIAGNOSTICS`, `TECHNICAL_ADMIN_VIEW`, `TECHNICAL_EXCEPTION_VIEW` and `AUDIT_VIEW` (`ProductAuthorizationPolicy`). It gives no document capability.
- **Which screens need it.** 19 endpoints require `PLATFORM_OPERATIONS`:
  - licensing (4);
  - processing storage (7);
  - deployment branding (5);
  - lifecycle purge (1);
  - platform admin health check (1);
  - product telemetry (1).
- **With the shared mode on, nobody can reach them.**
  - The platform role can never come through an entity's groups: the role catalogue and preflight refuse it, by design.
  - The legacy role mapping (`SECUREDOC_SECURITY_ROLE_PLATFORM_OPERATIONS_ADMIN` in `OidcRoleMapper`) is used only when the shared mode is off.
  - On top of that, every request first needs an admitted entity (`TenantBoundaryInterceptor`, then the shared-issuer branch). A person in the IT group but in no entity is refused before any platform check.
- **With the shared mode off** (one entity, legacy), the configured group maps to the platform role inside that single tenant. That stays as it is (frozen Enterprise Identity R1).

### 2.2 The proposal

- **A new install-level setting:**
  - `securedoc.security.oidc.platform-admin.group` (environment `SECUREDOC_SECURITY_OIDC_PLATFORM_ADMIN_GROUP`);
  - `securedoc.security.oidc.platform-admin.issuer`, which defaults to the main issuer.
  - **Default: empty, which means nobody has platform access.**
- **How it is checked on each request.** The verified token must come from the configured issuer, and its groups claim must contain the configured group exactly. The library gets a small rule, `PlatformAccess`, with its own `Reason` codes, so SDV uses the same check.
- **Why it can never come from an entity's mapping:**
  - the loader refuses the platform role (1.3);
  - the role catalogue refuses it at read time;
  - the platform check never reads grants.
  
  A customer's entity administrator therefore cannot make anyone a platform administrator.
- **Platform routes are an explicit list:** `/api/v1/platform/**`, `/api/v1/platform-admin/**`, the deployment-branding endpoints and the purge endpoint.
  - On those routes a person who passes the platform check gets a platform principal, with no entity and only the platform capabilities, and does not need an entity.
  - On every other route the platform group adds nothing, and the request is decided by entity admission alone, as today.

### 2.3 What a platform administrator can and cannot see

- **Can:** licences, processing storage, deployment branding, health, telemetry, and running lifecycle purge. These are install settings and counts, not documents.
- **Cannot:**
  - any package, document, finding, review item or redacted output;
  - any entity's policy or audit trail.
  
  These need an entity role. A person who is a platform administrator and also holds a role in entity A sees A's data through A's entity role, exactly as anyone in A does, and nothing of entity B.
- **Two points from today's code need the owner's decision** (question 4):
  - the platform role includes `AUDIT_VIEW` and `TECHNICAL_EXCEPTION_VIEW`;
  - some technical-exception views show package identifiers.
  
  **Recommended:** on platform routes these views return only counts and states, never package contents.

### 2.4 Correct for hosting later

- **In hosting**, platform staff sign in through their own staff space, a separate issuer in the hub (design section 8, item 13). The setting already names an issuer, so that is configuration, not a code change: there the platform issuer is the staff realm, not a customer's login system.
- **A customer's login system can never grant platform access in hosting.** The check requires the platform issuer, and customer tokens come from other issuers.
- **The proof** "a customer group with the same name gets nothing" is already a Phase 1 style check (P-07).

### 2.5 The frontend

- **A platform-only person** (in the IT group, in no entity) is refused at sign-in today: `/me/tenants` is empty, so the UI shows "Sign-in could not be completed".
- **Phase 3 lets that person in.** The UI then shows only the platform screens.
- **This is a change to the sign-in flow**, which is a frozen area (question 3).
  - **Smallest form:** a new `GET /api/v1/me/platform` answers whether this person has platform access. When the entity list is empty but platform access is true, the UI opens the platform screens instead of refusing.

## 3. Phase 4: machine integrations tied to one entity, and caching

Proof: section 11 point 4. A service account for one entity cannot push into the other.

### 3.1 Machine admission today, and the weakness (design section 8, item 7)

- **How it works.** In shared mode `resolveOidcIntegrationPrincipal` matches `integration_connections.client_principal` against the token's username: `preferred_username`, or `sub` when there is no username.
  - The match also requires an enabled `INGESTION_SOURCE` / `PUSH_API` integration with `JWT` or `OAUTH2_CLIENT_CREDENTIALS` authentication, on the entity's ACTIVE connection.
  - `MachineEntityAdmission` then requires exactly one match.
- **The weaknesses:**
  1. **The client principal is unique only inside one entity** (`uk_integration_connection_tenant_client_principal` is on `(tenant_id, client_principal)`). The same name configured in A and B gives two matches, so the machine is refused in both. It fails closed, but one entity's configuration can lock out another entity's integration.
  2. **`preferred_username` is a display-style name.** In some login systems an administrator can rename it, and nothing ties it to the client that obtained the token.
  3. **`/api/v1/scanner-intakes` is not on the machine path** (`TenantBoundaryInterceptor` routes only `/api/v1/external-intakes`). In shared mode the scanner bridge is treated as a person and refused.
- **The fix:**
  - Bind an integration to the token's **issuer and `sub`**. `sub` is stable for a service account: a Keycloak service account has a fixed id, and Okta client-credentials tokens carry the client id as `sub`.
  - Add `client_subject` and `client_issuer` columns to `integration_connections`, with a **unique index on `(client_issuer, client_subject)` across all entities**. One service account can then belong to only one entity, enforced by the database (a schema change, question 5).
  - In shared mode the machine match uses `(issuer, sub)` only. The old name match stays for the legacy single-entity mode.
  - The scanner-intake route is added to the machine path in shared mode. That is technical; I chose to include it, because without it the scanner breaks under shared mode.

### 3.2 Caching on the shared-login path

1. **First, remove the repetition.** `resolvePrincipal` runs in `TenantBoundaryInterceptor`, `CapabilityAuthorizationInterceptor`, `RoleAuthorizationInterceptor` and again in most controllers. In shared mode each run makes two database queries, grants and candidates.
   - **Fix:** resolve once per request and keep the result on the request (a request attribute keyed by the resolver), for both the human and the machine principal.
   - **Test:** counts the lookups per request (expect 1).
2. **Then cache the per-connection lookups,** not per-user answers.
   - **What is cached:**
     - the grants map and the ACTIVE-candidate set, for one `ConnectionKey`;
     - the machine binding for one `(ConnectionKey, issuer, sub)`.
   - **Not cached:** the decision for a person. It is still computed on every request from that person's verified groups and choice, so different people never share an answer.
   - **Where:** a library decorator, `CachingEntityLookups`, with an injectable clock, like the existing `CachingOidcConnectionBindingResolver`.
   - **For how long:** 30 seconds, the same bound the legacy resolver already has.
3. **How a change takes effect:**
   - **On the same server:** the role-mapping loader and the login-system activation and rollback paths clear the cache when they commit.
   - **On another server:** within 30 seconds, through the time limit.
   - **Covered changes:** a deactivated entity, a disabled login-system record, a changed mapping, a disabled integration.
4. **The proof that a cached answer never outlives a revocation by more than 30 seconds:**
   - **A library test:** after a revocation, the cached answer is still served before 30 s and refused at 30 s, with no path that extends the time. The cache entry's time is set once when it is filled and never refreshed by reads.
   - **Phase 1:** checks R-13 and R-14 already toggle entity B and wait 31 s. They become the runtime proof, named explicitly (C-01).

### 3.3 Leftovers from Phase 1b

- **The preflight call in `RequestContextResolver`: removed.**
  - Its "enabled" and "persisted" arguments are always true there.
  - Its "candidates contain memberships" check is always true, because both come from one map.
  - Its empty-role and platform-role checks are already enforced by `EntityGroupAuthorization`.
  - The library class `SharedIssuerPreflight` stays, for products that want it.
- **The id round trip: reduced to one conversion at the seam.** The resolver keeps the library's map, chooses with it, and converts only the chosen id and its roles to LexaVault types.
- **The guard:** the 13 P2a tests must pass unedited.

## 7. Technical choices I made (not questions)

- **Cache time 30 s**, the same as the existing resolver, with clear-on-write on the same server.
- **The machine identity claim is `sub`,** together with the issuer.
- **The scanner-intake route joins the machine path** in shared mode.
- **The library messages become neutral in Phase 2,** while LexaVault keeps its texts.
- **An entity with an invalid grant is refused for that entity only,** never for everyone.
- **One command runner in the backend jar,** reused by Phase 5's setup command.
