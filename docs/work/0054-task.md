# Task 0054: Identity bump to platform-core v0.7.0 (security fixes, last Spring Boot 3 release)

Written 2026-11-24 by the LexaVault design chat (owner approved). Queue task. Small. Standing rules (`QUEUE.md` rule 8). Report: `docs/work/0054-report.md`.

- **Why:** platform-core (board SH-25, SH-26) says apps still on Spring Boot 3 move to **`platform-core-v0.7.0`** now: the last Boot-3 release, with every Critical, High and Medium security fix found so far. LexaVault is on `v0.2.0` (identity only, LV-13/14/16).
- **Scope:** a version bump of the identity modules (and the setup jar, `backend/securedoc-setup`) from `0.2.0` to `0.7.0`. Nothing else of platform-core enters the app (LV-11: licensing use, notifications, crypto, erase log, case fields, integration, monitoring, model governance wait for `v1.0.0`). The app jar check in `Build-LexaVault-All.*` must still pass.
- **Read first:** `docs/releases/platform-core-v0.3.0.md` … `platform-core-v0.7.0.md` in platform-core (read only: GitHub or `C:\dev\platform-core`; never build or change it) for every breaking change that touches identity or setup: identity schema V4, messages starting with their code, hidden internal types, `forbidden-roles` not empty, development-key licences recognised, **SEC-7: a person's token is never accepted as a machine push caller** (check LexaVault's push-caller settings), licence trusted keys only from the app's build (dev keys only in a dev build: check the demo files and the setup wrapper still work locally).
- **What it brings for free (identity):** test sign-in and platform-level grants (v0.3.0). Turn on what LV-16 waited for: the **read-only "Test sign-in"** on the login-connection screen, and **`PLATFORM_OPERATIONS_ADMIN` through a platform-level grant** in the demo role mapping. The connection screen otherwise stays read-only.
- **Owner approvals given:** the identity schema migrations v0.7.0 requires (run by the schema step, never at startup). No other schema change, no new dependency.

## Prove it
Schema step on a fresh database and on one prepared like the owner's (identity V3 → latest); setup and demo step unchanged otherwise; sign-in works (LOCAL and OIDC against a throwaway Keycloak, as in 0041); test sign-in answers for the demo connection; full backend build with PostgreSQL tests on, `npm run test:standalone`, the no-redacted-value check, the compliance report check, the export end-to-end, the product-name guard.

**For the owner** (list in `QUEUE.md`): after merge, rebuild, `Start-LexaVault-OIDC.ps1 …`, then `Test-LexaVault-OidcSessionContinuity.ps1 -Username businessuser -PromptForPassword`.

## Decisions (2026-11-24, design chat, as recommended under LV-19; answers the session's stop)
1. **Allow exactly `platform-outbound-spring`, `platform-outbound`, `platform-errors` and Apache HttpClient 5** in the app, and add them to the app-jar check in `Build-LexaVault-All.*`. They are what `platform-identity-*` 0.7.0 itself needs (the safe outbound fetch for test sign-in, and the shared error shape); they don't integrate any other capability. Nothing else of platform-core enters the app.
2. **Licence keys from the build (SEC-12):** yes. The development public key used by the demo files is shipped **only in the development build** (a dev profile / dev resource set), and the setup wrapper and demo step use it there. A production build carries only the production trusted keys. Prove both builds: dev demo starts; production build refuses a development-signed licence.
